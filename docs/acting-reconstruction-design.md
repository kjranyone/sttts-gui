# 発話の演技を再構築するための設計案

## 目的と到達範囲

sttts は、話した内容を別の声で届ける際に、言葉に加えて発話の意図もできるだけ保つ。ここでいう「演技」は、間、速さ、強弱、ためらい、語りかけ方など、聞き手が意味を受け取るうえで重要な表現を指す。元の声質を複製することは目的に含めない。

最初の到達点は**表現の再解釈**である。同じ文字起こしでも、落ち着いた発話と切迫した発話から異なる合成結果を得られることを目指す。元音声の音高曲線、語ごとの長さ、息遣いを厳密に写すことは、現行の Irodori-TTS の入力だけでは保証しない。厳密な追従が必要なら、将来の音声変換・韻律条件付き合成エンジンを別経路として評価する。

利用者には次の二つの発話方式を提供する。

| 方式 | 使いどころ | 入力音声の扱い |
| --- | --- | --- |
| 明瞭に読み上げる | 速度と聞き取りやすさを優先 | 現行のテキスト中心の経路を保つ |
| 表現を反映する | 話し方を別の声に引き継ぎたい | テキストと元音声の特徴から発話計画を作る |

テキスト入力には元音声がないため、利用者が表現を選ぶか、声の既定設定を使う。自動推定された感情名を確定的な事実として表示しない。

## 認識精度に関する前提

現時点でローカル ASR は、この用途に必要な精度を満たしていない。音声から自動発話する主経路は **Gemini Transcribe Live** を前提にする。ローカル ASR は利用者が明示的に選ぶ実験・オフライン用途として残せるが、Gemini の失敗時に黙って切り替えない。読み違えた文字列をそのまま別の声で発することは、演技の再構築以前の品質問題になる。

このため、認識結果の型を全 ASR で揃えることは、各エンジンの品質が同等であることを意味しない。Gemini の接続エラーや空結果の発話は自動発話しない。画面では失敗を示し、再試行または利用者によるテキスト入力・修正を案内する。一方、**確定文字列にも誤認識はあり得る**ため、確定イベントを「内容が正しい」という保証として扱わない。ネットワーク未接続のままライブ発話を続けられるとは表示しない。

## 現状と制約

- [FinalJob](../backend/src/sttts_server/session.py) は 16 kHz の発話音声を保持している。VAD スレッドは重い処理をせず ASR ワーカーへ渡す。
- 現在の発話バッファは VAD の開始イベントから積み始める。発話の入り際や息を観測したい場合は、VAD スレッドに小さな先行バッファを持たせる必要がある。先行バッファは容量を固定し、マイクの open/close 手順を変えずに追加する。
- [ASR 確定時](../backend/src/sttts_server/app.py) は文字列と計測値だけを GUI へ送り、auto_speak も文字列だけで TTS を開始する。
- [TTS ジョブ](../backend/src/sttts_server/app.py) はテキスト、スタイル文、参照 WAV、seed を持つ。現状、スタイル文と参照 WAV は通常、発話間で固定される。
- Irodori-TTS はテキスト、参照音声、スタイル文、出力時間の条件付けを持つ。参照音声は話者とスタイルの両方に影響し得る。元の発話を参照音声へそのまま混ぜると、選択した声の一貫性を損ねる可能性があるため、初期設計では**元音声を Irodori の参照音声にしない**。[公式パラメータガイド](https://github.com/Aratako/Irodori-TTS/blob/main/docs/parameters.md)
- Irodori-TTS-v4.1-Small-MF は参照音声とスタイル文が矛盾すると品質が不安定になり得る。また、声・スタイルの忠実度はモデルカードのベンチマークだけでは評価されていない。[モデルカード](https://huggingface.co/Aratako/Irodori-TTS-v4.1-Small-MF)
- Gemini Transcribe Live は途中・確定テキスト、言語コード、任意の発話単位時刻を返すが、話者分離と単語時刻は Live 版では提供しない。演技分析をそのメタデータだけに依存させない。[Live Transcribe](https://ai.google.dev/gemini-api/docs/live-api/live-transcribe)、[応答スキーマ](https://ai.google.dev/api/live.md)
- 現行の [Gemini ASR 実装](../backend/src/sttts_server/engines/asr_gemini.py)は、VAD が発話を閉じてから Live セッションを開き、音声全体を一括送信する。partial も蓄積音声の再送であり、Live の逐次転写イベントを利用していない。準リアルタイム化では、マイク取得中に音声を非同期キュー経由で同じ Live セッションへ逐次送り、ローカル VAD の終了時に `audio_stream_end` で確定させる構成を評価する。送信処理で VAD やレベルメーターを塞がない。

## ASR と表現分析の役割

**Transcribe Live 一つの応答から感情やリズムを取り出すことはできない。** 次の結果を同じ発話 ID で結合する。表現推定器は候補を評価して選び、複数を必須にはしない。

| 入力 | 担当 | 結果 |
| --- | --- | --- |
| 元音声 → Gemini Transcribe Live | 読み上げる言葉の確定 | VERBATIM の原文、必要なら言語と発話時刻 |
| 元音声 → ローカル SER または Gemini 音声理解 | 聞き取れる表現の候補 | 限定した表現タグ・不明の可能性 |
| 元音声 → ローカル音響分析 | リズムの測定 | 無音の位置と長さ、相対的な速さ・強さ |

Gemini の[音声理解ガイド](https://ai.google.dev/gemini-api/docs/audio)には音声から感情を構造化出力する例がある。ただし、これは **Transcribe Live とは別の呼び出し**であり、感情タグの妥当性や本アプリでの遅延は未検証である。準リアルタイムの候補としては、元音声だけを使う分析を転写と並行して開始し、「音声から聞こえる話し方だけを短く記述する」「根拠が弱ければ不明を返す」「文意から感情を決めない」と指示する。音声理解モデルが別の文字列を提案しても、発話内容の正本を置き換えない。

ローカル SER の候補には、9 種の感情を分類する [emotion2vec+](https://github.com/ddlBoJack/emotion2vec) と、日本語を含む音声から転写と感情タグを返す [SenseVoiceSmall](https://github.com/QwenAudio/SenseVoice) がある。SenseVoiceSmall を表現分析に使う場合も、転写の正本は Gemini の結果とする。日本語での表現判定、CPU での処理時間、追加モデルのメモリ消費を評価してから採用する。SER は機械学習モデルであり、無音・長さ・強さを測る信号処理とは区別する。

表現推定器のスコアを「怒り 87%」のような校正済み確率として扱わない。リズムも「ゆっくり」というモデルの感想ではなく、元音声から測った長さと間を使う。ローカル音響分析は録音中から進め、SER を有効にする場合は ASR の転写と並行して音声を分析する。締切内に届いた候補だけを合成計画へ反映する。表現推定の自動適用は評価後の段階であり、初期実装では利用者が選んだ表現と音響観測を使う。

## 発話を表す内部データ

ASR の返り値を文字列から、発話を追跡できる結果へ広げる。すべての ASR エンジンは同じ型を返し、存在しない情報は空値にする。結果には使用エンジンと成功・失敗を明示し、異なるエンジンの結果を同等の確からしさとして扱わない。後方互換のための二重 API は作らない。

| 概念 | 主な項目 | 用途 |
| --- | --- | --- |
| Transcript | 原文、読み上げ文、言語、出所 | 内容の保持。原文と整形後の文を混同しない |
| SourceAudio | 発話 ID、16 kHz 音声への一時参照、区間時刻 | 局所的な音響分析。既定では保存しない |
| AcousticObservation | 発話ごとの無音区間、相対速度、相対音量、使える場合の音高変化 | 観測値。感情ラベルとは分ける |
| DeliveryIntent | 「ためらう」「強く訴える」等の候補、根拠、推定度、手動修正 | 合成に使う表現上の判断 |
| VoiceIdentity | 利用者が選んだ参照音声、既定の声設定 | 発話をまたいで保つ声の同一性 |
| RenderPhrase | 読み上げる文字列、出力順序、スタイル文、長さ倍率、後続の間 | TTS と再生キューへ渡す確定計画 |

音響観測は話者内・同一セッション内の相対値で扱う。音量が大きいだけで「怒り」、音高が高いだけで「喜び」と判定しない。表現意図の自動推定は候補として扱い、利用者の指定を優先する。

## 処理の流れ

1. VAD は従来どおり発話音声を FinalJob として確定する。マイク、レベルメーター、ASR ロードとの並行性を変えない。表現反映方式で Gemini を使う場合は、言い直しやフィラーが消える SMART ではなく VERBATIM を原文の既定とし、整形した読み上げ文は別に保持する。
2. Gemini Transcribe Live と軽量な PerformanceAnalyzer を VAD スレッドの外で並行実行する。表現推定を有効にした段階では、ローカル SER または Gemini 音声理解も転写と並行して元音声を分析する。同じ発話 ID で結果を結び、接続・認識エラーと表現分析エラーを別々に扱う。
3. PerformanceAnalyzer はまず無音区間、RMS 包絡、発話長を抽出する。安定して算出できる場合だけ音高関連の特徴を追加する。音響特徴から複雑な感情を直接断定しない。
4. UtteranceCoordinator は Gemini の確定文字列、SER または音声理解の表現候補、音響観測を発話 ID で結合する。**表現分析だけ**が期限内に終わらない場合は、待ち続けず、認識済みのテキストを明瞭に読み上げる。Gemini の認識に失敗した場合は、表現分析が成功しても自動発話しない。
5. 最初の実装では**VAD 発話全体**の表現を扱い、現在のチャンク分割後も同じ表現計画を適用する。発話内の無音を特定の文字列へ結び付けるには時刻アラインメントが必要で、Gemini Live の発話単位時刻だけでは足りない。句ごとの表現と間は、アラインメントの精度を検証できてから追加する。ローカル ASR に再転写させて境界を推定することを前提にしない。
6. 選択された声を固定したまま Irodori のスタイル文と duration_scale を発話単位で与える。句ごとの計画が利用可能になったら、チャンク境界を元の間に合わせ、句間の無音を再生キューで表現する。値は評価後に決める範囲へ制限し、指定が効かないモデルでは無理に効果を表示しない。
7. 句ごとの生成結果を現行と同じ順序・キャンセル規則で再生する。発話が終わったら元音声への一時参照を解放する。

声の参照音声がある場合、スタイル文は表現や場面を記述し、声質・性別など声の設定と衝突しやすい記述を自動追加しない。caption のみで声を指定する場合は、声の記述と一時的な表現を別々に管理してから一つの caption を構成する。

実装時は `session.py` の FinalJob と ASR 結果型、`app.py` の発話結合・TtsJob・投機結果の一致条件、TTS の発話単位 sampling、GUI の発話表示を変更点とする。GUI に渡す要約を増やす際は Rust と Python のプロトコルを同時に更新する。元音声の配列は backend 内部に留める。

## レイテンシと失敗時の動作

「明瞭に読み上げる」は現行の初音経路を維持する。「表現を反映する」は、解析待ち、句の確定待ち、合成待ちをそれぞれ計測し、増分を画面で説明できるようにする。解析の期限と許容遅延は実測で定める。

初期段階では表現反映方式の投機的 TTS を無効にする。将来有効化する場合は、テキストだけでなく表現計画と声の条件が一致した結果だけを再利用する。分析エラー、未対応モデル、解析キューの混雑時は、**Gemini が確定文字列を返した発話だけ**明瞭読み上げへ戻る。Gemini の失敗をローカル ASR で隠さない。キューの混雑をマイクの停止やデバイスの再オープンで解決しない。

元音声は既定でメモリにのみ置き、解析・合成計画の確定後に解放する。ログと GUI⇄backend プロトコルへ生音声を載せない。Gemini 音声理解へ元音声を追加送信する機能は、転写用の送信とは別の設定として明示する。

## UI への反映

- 主画面では「何を話したか」「どう伝えるか」「どの声で届けるか」を分ける。チャットの二者会話としては見せず、一つの発話の入力と再構築結果を対応付ける。Gemini の接続状態と、文字起こし失敗によって自動発話が止まった状態を明確に表示する。
- 発話方式とは別に、認識文を「即時発話」するか「確認後に発話」するかを選べるようにする。即時発話では誤認識を事前には防げないため、直近の発話を止めて訂正し再発話する操作を近くに置く。確認方式では待ち時間を明示する。
- 発話カードには原文、読み上げ文、元音声から観測した間、適用予定の表現を示す。推定された表現は修正・無効化できる。ライブ自動発話中は操作を要求しない。
- 常時表示する設定は発話方式と声を中心にする。モデル、細かな sampling、分析値は詳細設定・診断へ置く。
- 元音声と合成音声を聞き比べられる場合でも、元音声は既定で永続保存しない。聞き比べが必要な保存操作は利用者が選ぶ。

## 段階的な実装・評価

1. **データ経路**: Transcript と SourceAudio の発話 ID を保ち、分析なしでも Gemini の確定文を明瞭に読み上げられることを fake ASR / fake source / mock TTS で確認する。Gemini の失敗時にローカル ASR が自動起動せず、その発話が自動合成されないことも確認する。
2. **発話全体の表現**: 速度や音量などの観測を持ち、利用者が選んだ表現を発話単位の caption に渡す。合成の内容、順序、キャンセル、停止時の音声解放、モデルごとの効果と声の安定性を確認する。
3. **句単位の再構築**: 無音位置と Gemini の文字列を対応付けられるアラインメント手段を評価する。[Gemini の録音ファイル向けモデル](https://ai.google.dev/gemini-api/docs/transcribe)は単語時刻を取得できる候補だが、追加リクエストの遅延と費用を測ってから採用を決める。確実な境界だけを使って句分割、句ごとの表現、句間の無音を反映する。対応が曖昧なら発話単位の計画へ戻す。
4. **表現の推定**: ローカル SER と Gemini 音声理解を候補として評価し、元音声を聞いた人の判定との一致、CPU 実行時間、メモリ使用量、初音遅延を測る。十分な評価資料が揃ってから自動適用を追加する。誤推定時には無理に演技を付けず、利用者が修正できるようにする。
5. **合成方式の判断**: Irodori で達成できるのが「意図の再解釈」までなら、その名称を守る。元音声への忠実な韻律追従を要件にする場合は、別エンジンを比較する。

評価では、同じ文を異なる話し方で発した組を使い、内容の正確さ、表現の識別しやすさ、選択した声の一貫性、自然さ、初音までの時間を別々に見る。自動テストは fake source / mock engine と保存済みの合成信号で完結させる。実マイク・実 GPU を使う確認は既存のハードウェア検証ポリシーに従い、GUI からのみ行う。

## まだ決めるべき製品判断

- 「演技」は元の話し方に似せることを優先するか、聞き手に同じ意図が届くことを優先するか。
- 自動発話では、原文の言い直し・フィラーをどこまで残すか。表現反映方式では SMART 整形済みテキストだけを唯一の原文にしない。
- どれだけの初音遅延を許せるか。表現の改善とレイテンシの双方を見て決める。
- 合成音声の品質を優先して、演技の反映が難しい発話では表現反映を控えるか。
